# Nightmare Vision source title and transition contract

Audit date: 2026-10-06
Donor: `fnf_sources/NightmareVision`, revision `733165c42ca71eb0961a70e4173b2d81ba4a29ea`
Scope: read-only source contract review. No donor files, production code, or importer code were changed. No build or runtime result is claimed.

## Donor contract

`TitleState` has no explicit constructor; it inherits `MusicBeatState.new()`. Its static `init()` clears stored and unused memory and may redirect to `FlashingState` when the flashing preference has not been selected. `create()` then selects intro text, calls `initStateScript()`, and runs `startIntro()`. `startIntro()` runs `onStartIntro`, constructs the title visuals, and calls `onCreatePost`. The normal enter path requests `FlxG.switchState(MainMenuState.new)`, passing a constructor closure. See `source/funkin/states/TitleState.hx:17-50, 67-120, 142-155`.

Custom title and menu scripts are selected by `meta.json.stateRedirects`, not by substituting the host's title state. Donor `FunkinGame.switchState()` destroys the prior state, creates the requested class, reads its simple class name, and checks the current config. When a matching `scripts/states/<scriptName>` file exists, it destroys the intended state and constructs `ScriptedState(scriptName)` instead. The replacement constructor is retained as the new state's constructor. A missing redirect script logs a warning and leaves the requested native state in place. See `source/funkin/backend/FunkinGame.hx:26-96`.

`MusicBeatState.initStateScript()` derives the default script name from the actual state class, resolves `scripts/states/<name>` through `FunkinScript.getPath()`, and parents the group to that state. `ScriptedState.new()` binds the script and calls `onLoad` before the state's `create()`; `create()` calls `onCreate`. See `source/funkin/backend/MusicBeatState.hx:52-82` and `source/funkin/scripting/ScriptedState.hx:6-27`. State scripts are executable source state wrappers, not callbacks attached to a native alias.

The donor entry point is `Init`, not `TitleState`. `Init.create()` loads preferences and highscores, calls `Mods.pushGlobalMods()` and `Mods.loadTopMod()`, configures engine services, and populates `ModPlugin` before switching to the startup state from `Main.startMeta`. See `source/Init.hx:19-83` and `source/Main.hx:22-60`. Thus a source plugin's `onLoad` can change the selected package before the first TitleState constructor is requested.

`FlxG.switchState` receives a `NextState` constructor, and the donor's `FunkinGame` runs the switch in this order: reset cameras and inputs, dispatch pre-switch, destroy the old state, construct the new state, apply a state redirect, dispatch pre-create, create the new state, then dispatch post-switch. `CoolUtil.switchState(next, transition)` temporarily sets both transition globals, requests the same FlxG factory, and restores both globals on `postStateSwitch`. `FlxG.resetState()` is used directly by gameplay, pause, editor, and hot-reload code; it is not a source `Utils.reset()` helper and does not run the full `Init` sequence.

`Mods.loadTopMod()` clears `currentModDirectory`, parses the enabled list, selects the first enabled package, then calls `applyModConfig()`. `applyModConfig()` returns immediately if no pack is found. Otherwise it first assigns `currentModConfig`, initializes `ModOptions` for `currentModDirectory`, then applies window title/icon, transition in/out, Discord RPC ID, default font, and UI/countdown/combo/rating prefixes. `FunkinGame` later reads `currentModConfig.stateRedirects`. See `source/funkin/Mods.hx:332-400` and `source/funkin/backend/FunkinGame.hx:51-76`.

The D-Sides `ModsState.makeTopMod()` flow sets `currentModDirectory`, updates the mod list, and loads the top mod in that order. Returning after the top mod changes stops menu music, corrects the selected top mod, clears `TitleState.initialized` and `closedState`, then requests a new `Init`. See `source/funkin/states/ModsState.hx:114-130, 202-208`. `Mods.updateModList(top)` does not forward its formal `top` argument; `getListAsArray()` defaults to `currentModDirectory`, which is why setting the directory before the update is significant. See `source/funkin/Mods.hx:267-329`.

`ModOptions` is process-static in the donor, but its data is bound per mod as `mods/<mod>`. `init(modName)` flushes the previous mod only when the name changes, clears/reloads `optionData`, closes the save, and validates option order. `add()` permits the active package or an enabled global package and flushes the saved option table after registration; `setValue()` mutates the current option. See `source/funkin/data/ModOptions.hx:106-240`. The Options screen builds a `ModOptionsSubState` from the current option list.

## Retained reset example

The retained local D-Sides source snapshot at `tmp/dsides-redux-import-regression-long-runtime/CammieEngine-windows-x64/import-cache/sources/868ed5ac7632b1d4680cfbc200011130a7070696bc62ef3c9a3494142cba86ad/` contains two source package labels, `old-dsides` and `new-dsides`. Its `old-dsides/scripts/plugins/Utils.hx` imports `funkin.states.TitleState` and `funkin.Mods`. In `onLoad`, when the selected directory is `old-dsides`, it calls `reset()` and then requests `FlxG.switchState(()->{new TitleState();})`. `reset()` selects `new-dsides`, updates the list, and calls `Mods.loadTopMod()`. This is a real plugin lifecycle transition and exercises a constructor closure, selected-label change, list order, config reload, and title-state reconstruction.

The retained `new-dsides/meta.json` contains redirects for TitleState, MainMenuState, StoryMenuState, FreeplayState, CreditsState, and OptionsState. The retained `new-dsides` subtree does not contain the corresponding `scripts/states` files; the donor behavior for those missing paths is warning plus native-state fallback, not a custom state execution. The retained `old-dsides/scripts/states/MainMenuState.hx` separately demonstrates a state script switching to `PlayState` from `onUpdate`. These files are useful structural evidence, not proof of a fully rendered imported title/menu flow. No production behavior should special-case either package label.

## Current host boundary

The current host's `Main` constructs a standard `FlxGame` with `TitleState` directly (`source/Main.hx:43-68`); it does not run the donor `Init` and `FunkinGame` lifecycle. The NV `NightmareVisionModsContext`, `NightmareVisionModFamilySession`, `NightmareVisionPaths`, owner save/options facades, and script groups exist, but the chart owner/session is initialized from `PlayState.initializeNightmareVisionScripts()` (`source/PlayState.hx:1132-1249`). `NightmareVisionSourceBindings.bindOwner()` and `bindGameplay()` likewise seed the gameplay interpreters. There is no owner-scoped source state factory or source menu session established before TitleState.

`NightmareVisionScriptDiscovery` deliberately limits its current plans to plugins and chart scopes; its class documentation explicitly lists dynamic loads, imported modules, and menu scripts as separate gaps (`source/NightmareVisionScriptDiscovery.hx:31-46, 175-177`). `NightmareVisionPluginHost` supplies persistent plugin `onStateSwitch` and `onStateSwitchPost` notifications, but it is mounted from the PlayState script initializer (`source/NightmareVisionPluginHost.hx:34-75`, `source/PlayState.hx:1132-1249`). `NightmareVisionFlxGView` forwards FlxG calls while replacing `save`; it does not bind a source owner/session to a requested state constructor (`source/NightmareVisionFlxGView.hx:18-73`). HXC and Codename state factories are owner-scoped, but use their own parser, manifest, and wrapper contracts; they are not NV source state implementations (`source/HxcStateFactory.hx:50-108, 270-371`, `source/CodenameModStateRuntime.hx:12-110`).

`NightmareVisionModsContext.applyModConfig()` is being extended by the separate config workstream. State creation still needs to consume that selected config at the correct boundary and keep config effects associated with the source owner. Source/global title, icon, transition, Discord, Paths prefix, and option state must not leak when switching to an unrelated owner.

## Smallest coherent next package

1. Create one source state session before the title state is constructed. It should retain the authenticated imported owner and catalog-authorized package roots, selected source label, Mods/config/options, Paths/assets, save facade, and persistent plugin group. A changed source label updates scoped lookup; it does not navigate by itself.
2. Add a source `FlxG` and `CoolUtil` transition adapter that accepts constructor factories, not preconstructed state aliases. It should carry the same authorized session through TitleState, MainMenuState, FreeplayState, PlayState, and `resetState()`, while preserving the donor FlxGame switch ordering and transition restoration.
3. Add a central source state redirect path matching `FunkinGame`: inspect the requested state's class name, resolve only the selected package's authorized `scripts/states` entry, and instantiate an owner-scoped script-state wrapper. The wrapper must run `onLoad` after its parent is bound, `onCreate` after native create, lifecycle/update callbacks in source order, and `onDestroy` before dropping its interpreter. Missing redirect files should retain the intended native state with a clear source-style diagnostic.
4. Keep persistent plugin and family asset leases through pre-switch, old-state teardown, and post-switch when the destination uses that family. Release state-local interpreters/views at state destruction. Restore global process effects when leaving the source owner.
5. Verify with a generated two-package family fixture that runs the retained reset sequence without package-name production cases: old package `onLoad`, directory/list/config change, TitleState constructor closure, configured redirect present and missing cases, `resetState`, then a switch into and out of source gameplay. Validate native rendered menus/audio and repeated visits separately; headless state factories do not prove visual parity.

This is a bounded state/session/factory package. Full menu redesign, arbitrary compiled-class reflection, and unsupported nested-family inference are outside its contract.
