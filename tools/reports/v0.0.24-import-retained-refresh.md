This tests a real update-triggered regeneration with unchanged conversion semantics, not a particular historical converter migration.

The test is muted on a never-activated Windows desktop, with a 60 FPS cap. No build or regression run overlaps the timed refresh. A separate save root and restored private options isolate normal user data. The benchmark's private RELEASE_TAG is v0.0.24. The full roadmap remains open and nothing is published.

## Harness correction

The opt-in CAMMIE_IMPORT_REFRESH_STOP_ON_COMPLETE mode now uses the separate import wait window even without selecting a song. It requires an idle, changed, complete refresh with an empty queue; a busy/unchanged/queued/missing result cannot pass when the menu timer expires. It emits two-second status observations and a distinct completion event. Ordinary browsing/gameplay timing stays unchanged. This prevents a generic menu timeout from becoming false refresh-success evidence.

All three affected harness tests passed and the canonical Windows build passed. The full suite ran 2,752 tests across 924 modules in 351.8 seconds, with 344 skips and one failed module. Windows Application Control blocked the WinRT native directory-enumeration fixture launch (WinError 4551), including an unchanged isolated retry. No security settings were changed. The failure is a validation gap, not a passing result. Logs: `tmp/v24-refresh-harness-focused.log`, `tmp/v24-refresh-harness-suite.log`, `tmp/v24-refresh-harness-retry.log` and `tmp/v24-refresh-harness-build.log`.

## Bounded route cache candidate

`ImportIO` now caches lexical path classification within its existing per-thread transaction scope, bounded at 4,096 entries and cleared when that scope ends. Immutable install/stage roots make these classifications reusable. File existence, staged precedence, masks, removals, contents, symlink checks and publication integrity remain live. Windows drive-relative and root-relative paths bypass the cache because their expansion depends on the current directory.

The focused tests exercise actual routing reuse, capacity, nested scope isolation, live create/change/delete/recreate behavior, invalid traversal, and Windows relative-drive handling. Five tests passed with one existing symlink privilege skip. The canonical build passed. The full suite ran 2,753 tests across 924 modules in 348.6 seconds with 344 skips. Its sole failing revision test overlapped the temporary diagnostic revision change; after production revision 3 was restored, that unchanged test passed. The earlier Windows Application Control fixture passed in this suite. Future diagnostic revision builds must follow, rather than overlap, the full suite.

The candidate measurement restores the original valid revision-3 manifest and exact original registry bytes, verified against their original receipt hashes. Other owned files were unchanged, as independently verified after the baseline. Completed transaction journals remain intact; recovery validates each against its own receipt without changing installed output. The candidate diagnostic uses revision 4 only to trigger the same ordinary update path. Production source and executable were restored before launch. The candidate completed successfully in 468.959 seconds from launch and 453.020 seconds in the worker, versus baseline 498.266 and 482.457 seconds. This is 29.307 seconds less launch-to-completion time (5.9%) and 6.1% less worker time in this single paired comparison. It is an observed end-to-end result for this collection, not a guaranteed gain for every installation. All 24,702 candidate output files were byte-identical to the baseline refresh output, and independent SHA-256 verification found no installed-file mismatch. The candidate commit receipt also matched its manifest. No diagnostic revision remains in production.

Evidence: `tmp/v24-route-refresh-proof.json`, `tmp/v24-route-refresh-proof.log`, `tmp/v24-route-refresh-input/proof.json`, `tmp/v24-route-binary-isolation.json`, `tmp/v24-route-refresh1-native.log` and the private runtime's `tmp/v23-historical-fields-route1.{jsonl,process.log}`. No build, suite or hashing workload overlapped the timed run. Both native runs are terminal successes; there is no live refresh process to resume.

The collection still takes almost eight minutes to refresh. Future work should profile the remaining scan/conversion calls and confirm improvements across independently installed packages, with another alternating measurement when evaluating the next candidate. The prior 26% scan-only gain is separate from this paired route-cache comparison.

Keep source verification, local-edit protection, readiness locks and gameplay pausing intact. Laptop GPU improvement remains small and further GPU work is still required.

### Newly measured responsiveness gap

Frame telemetry recorded 12,512 ms candidate and 10,324 ms control maximum update costs near the completion handoff in FreeplayState, followed by roughly 1.5-second spikes. Faster worker throughput has not solved menu responsiveness. Freeplay calls ImportRefreshManager.browseTick and may recreate the state when the generation changes; tryHandoff calls ModuleFunctions.completeImportOnMainThread, which invalidates shared caches and synchronously calls DifficultyManager.addSongSupport for every imported song. This is a concrete profiling target, not yet proof of which nested call consumed the stall.

Next isolate and fix the shared main-thread completion work while preserving readiness locks, atomic visibility and current difficulty metadata; do not move mutable global-cache operations unsafely onto the worker. Independently installed package coverage and further GPU work remain open. The laptop GPU/resolution question is optional and pending. All original compatibility, imported-menu, management, categories/favorites, Freeplay, sorting and graphics-fidelity goals remain required. Nothing published.
