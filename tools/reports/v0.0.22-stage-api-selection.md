# Nightmare Vision Stage API selection and scene integration

## Scope and source contracts

Development v0.0.22, following the already published v0.0.21. This checkpoint extends the explicit constructor work in [the preceding report](v0.0.22-legacy-stage-constructor.md). It does not publish another release.

Historical NV revision `54c53faa9493b1de88051fda7fcb7ff69e4f3950` uses `gameObjects.Stage`, a native group with separately scene-owned characters and foreground. Modern revision `733165c42ca71eb0961a70e4173b2d81ba4a29ea` uses `funkin.objects.Stage`, a native container owning its character groups. The adapters share owner services, paths, interpreter modules and host scene helpers while retaining these different ownership contracts.

The importer's existing bounded executable probe now recognizes exact qualified Stage class identities, requiring authenticated NV engine markers in the same executable. Mixed, absent or unproven class evidence remains unknown. Class-only helper executables cannot stop engine discovery. Authenticated content packages and explicitly selected core assets inherit the enclosing game's identity; no chart name, mod name or HUD artwork selects the adapter.

The importer stages `__cammie_nv_stage_api.json` with a schema version and installed owner identity using the existing generated-output writer. NV import revision 12 requests retained-source regeneration. Runtime selection reads only this installed metadata, rejects malformed or different-owner data, and keeps the existing modern default for unknown evidence. Qualified old and modern constructor imports remain available independently.

PlayState loads callbacks through the shared script group and mounts the selected source Stage model. Shared scene helpers route addBehind operations, stage metadata and script release. Replacement preserves actor identity/state, the scene slot and separately owned legacy foreground, with component coverage for one-time cleanup. Legacy Lua Stage construction and broader source-controlled mounting/cancellation remain open.

## Verification design

Executable Haxe fixtures exercise the actual scanner, generated-output conflict handling, owner-profile reader, interpreter bindings and scene adapter. Coverage includes old/new/mixed/prefix-only/unproven identities, authenticated parent inheritance, explicit core selection, owner isolation, native group identity, onLoad arguments, scene order, addBehind placement, script registration/release and both source models' stage replacement. These component checks do not certify every native draw/destructor path.

The native harness now has a separate bounded Freeplay import-wait budget (`--smoke-freeplay-wait-ms`). It waits on the actual row readiness decision before its sole confirmation, then keeps the requested gameplay sample duration. Ordinary menu and direct-gameplay timing remain unchanged. Earlier 60-, 180- and 600-second native attempts expired while migration was still progressing and are not gameplay acceptance evidence. The final import-wait bound is thirty minutes; gameplay retains its twenty-second sample.

## Muted native evidence

The private-desktop retained refresh completed conversion and publication at NV import revision 12. Its committed receipt contains all eleven owner API profiles, and their installed bytes match the receipt hashes. The run took 513.651 seconds before the driver reported a target-search failure immediately after Freeplay rebuilt its list. It never accepted the chart during that run. This establishes successful refresh publication, not a successful uninterrupted refresh-to-gameplay smoke.

The driver had incorrectly measured every later search from the first menu entry, so moving a previously found row after a long wait caused immediate failure. Each uninterrupted search now has a separate twenty-second deadline. An executable regression checks late list rebuilds, reselection, genuinely removed targets, acceptance and ordinary browsing. Package readiness is still authoritative and is never bypassed.

Subsequent ordinary Freeplay runs on the committed isolated installation both observed `availability.ready=true`, sent confirmation, reached PlayState and completed their twenty-second samples: 60 FPS in 30.685 seconds and unlimited FPS in 32.532 seconds including startup (`tmp/v22-stage-ready-native-60.log`, `tmp/v22-stage-ready-native-0.log`). ## Known gaps and next work

The historical `flxanimate` dependency is version 3.0.4 in the pinned old NV Project.xml. Its constructor, `anim.addBySymbol`, playback and ownership contracts require comparison with the installed `flixel-animate` backend before adaptation. Reuse the existing `PsychFlxAnimateCompat`/controller and NV owner-scoped atlas services where their semantics agree; the old call signature is not interchangeable with the installed controller. `PsychVideoSprite` and the historical `gameObjects.shader.ColorSwap` uniforms/outline behavior also remain incomplete. Missing source effects must be implemented through shared services and dialect adapters, not replaced with chart-specific placeholders.

The prior committed isolated receipt contains 30,501 files and 3,074 distinct content hashes. Ten owners each have 2,735 core files: 27,350 core outputs with 2,681 distinct hashes. The new metadata raises this regeneration to 30,512 outputs. These metadata-only counts are recorded in `tmp/v22-stage-core-materialization-profile.json`; they are not a controlled timing benchmark. The real retained-package refresh materializes and checks these outputs, including repeated shared core content. Profile repeated authenticated core work before designing reuse; preserve retained arbitrary assets, independent owner edits, publication and readiness guarantees.

Phase 2 is unfinished. Imported menu flows, mod management, categories/favorites, dense Freeplay, correct icon/star behavior, independent group/chart sorting and quality-preserving performance all remain required.
