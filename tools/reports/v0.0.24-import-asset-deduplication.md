# Import asset-candidate deduplication

Local v0.0.24 performance checkpoint, 10 October 2026. All changes are in the shared importer. No chart/mod content or graphics changed.

## Evidence that selected the change

A content-validated, bounded implementation-JSON parse cache was tried and removed. It retained live reads, per-song root resolution, repeated malformed-file diagnostics and scan cleanup, but the real scan took 120.679 seconds versus 121.080 seconds for the preceding baseline. That is not enough gain to justify retained parsed objects and additional cache logic. The experiment and passing focused fixture are archived only in tmp/v24-json-cache-rejected. Production contains none of that cache.

An isolated diagnostic build then measured the current JSON inspection path over 3,989 documents (5,790,028 characters): 0.178 seconds reading, 0.285 seconds parsing, 31.626 seconds inspecting asset references, and 32.942 seconds total including candidate filtering. This is diagnostic attribution with timer overhead, not a production speed measurement. The diagnostic source/executable are isolated under tmp/v24-json-profile-bin; production files were restored before launching it. Evidence is the JSON_SCAN_PROFILE record in tmp/v24-scan-candidate/CammieEngine-windows-x64/tmp/v23-historical-fields-json-sections-profile.process.log.

## Shared change

scriptCandidatesForToken appended each candidate through uniquePush, which normalized all earlier paths again to detect duplicates. Large Auto searches therefore performed quadratic normalization work. It now reuses the existing uniquePushKeyed helper with a function-local key set. Ordered search paths, normalization rules, first spelling, asset aliases, owner roots, absolute/UNC handling and current filesystem checks remain unchanged. The set is discarded when candidate generation returns; there is no new retained cache.

The regression fixture compares complete ordered candidate arrays with the previous algorithm for image, icon, sound, Packer, relative, drive and UNC paths, duplicate/case-variant roots and empty references. Large searches require over ten times fewer key normalizations. Separate lookups verify owner isolation. Forty related tests passed with one existing filesystem skip; the canonical Windows build passed.

## Native comparison

The first production candidate completed the same full Psych collection scan in 93.180 seconds, versus the preceding 121.080-second baseline. All 675,316 normalized report lines are byte-identical after excluding only the Generated timestamp, SHA-256 dad6dc1b6fc9e94ceafaa67d22dc4876cd26a16f5a07a65a528a87e1680d877c. Both found 459 candidates and queued 242 songs with zero scan errors. The saved-baseline control ran afterward in the same install and took 121.362 seconds, with the same full report. This confirms a 28.182-second (23.2%) scan reduction in this matched comparison even with the baseline receiving the warmer run order. Evidence: tmp/v24-asset-dedupe-comparison.json and its referenced candidate/control proofs. The canonical export executable hash matches the measured production candidate.

All native runs were muted on a never-activated private Windows desktop. No build, regression suite or hashing workload overlapped timing. This measures scan work, not conversion/publication or a complete post-update refresh. Prior conversion diagnostics and the laptop GPU bottleneck remain unresolved. Preserve all broader roadmap goals. Nothing published.

The canonical build and related tests also passed. git diff --check and the punctuation guard passed.
