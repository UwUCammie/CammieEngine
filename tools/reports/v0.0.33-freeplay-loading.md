# v0.0.33 Freeplay difficulty listings and loading progress

Development checkpoint, 12 October 2026. No release is authorized or published by this work.

## Requested behavior and implementation

The host Freeplay sorting menu no longer exposes a selectable comparison difficulty. Difficulty Rating sorting expands a song into one lightweight presentation identity per available difficulty and orders each listing by its own integer rating. Up/Down selects those chart listings; Left/Right retains difficulty selection and immediately relocates the view to the selected difficulty's position. Alphabetical and other ordinary sorting retain their song listings. Favorites remain first, with independent group ordering, existing search/category filters and authoritative readiness/launch checks.

The song registry and launch indexes remain canonical. Only a bounded visible chart window allocates compact display rows. Stable song and named-difficulty keys retain unchanged compact row objects through ordering rebuilds, and applied availability snapshots refresh every visible chart's disabled presentation. The selected card retains the existing icon, source details, scores and difficulty stars.

Song loading removes the redundant work/status and scene-detail text shown in the reported screenshot. The artwork, heading, selected-song information and progress bar remain. Progress records completed scene-construction operations, chart-note rows, resource loads, teardown operations, bitmap-cache retirement and menu construction. Planned operations establish the denominator; dynamically discovered resources enroll and complete together. Phase ranges and a monotonic displayed fraction describe completed work, not elapsed duration or an estimated remaining time.

Construction and authored script callbacks remain synchronous. Completed-work checkpoints may present only the owned loading overlay through the existing native OpenGL renderer and native window swap. They do not render the partially built Stage, dispatch frame/timer/input events or update gameplay. Presentation is throttled to at most 30 Hz while work accounting continues at every recorded boundary. Repaints stop once the ready handoff has completed.

## Rendering and progress limits

The overlay presentation uses private APIs verified against pinned Lime 8.3.2 and OpenFL 9.5.2 on the native C++ OpenGL path. It requires a ready, nonzero viewport, the existing back-buffer renderer and no active render target, clipping or masking stack. It preserves renderer/context cleared and present bookkeeping, including exception paths. Context3D APIs keep OpenFL's GL cache truthful; this restricted idle boundary is not a general GL-state snapshot for arbitrary rendering callbacks. Unsupported rendering paths continue normal lifecycle presentation instead.

Granular work units measure completed operations, not equal execution costs. An individual blocking image/audio decode, source script or other operation can still pause the bar until it returns. The 30 Hz throttle reduces repaint overhead and never invents progress. The probe establishes visible movement inside synchronous work and the absence of nested game/frame updates at these checkpoints; it does not establish smooth movement through every possible imported callback or decode.

All broader compatibility, imported-menu continuity, management, fidelity and performance roadmap goals remain open unless their existing reports explicitly close a bounded gate. The user's separate playing installation is outside this checkpoint's changes.
