# Retained refresh discovery profile

Local v0.0.24, 10 October 2026. Diagnostic evidence, not a new production speedup.

## Method and completed transaction

An isolated native build added coarse timing around shared root discovery, each root's song discovery, candidate gathering and duplicate selection. The private fixture advanced normally from valid diagnostic common revision 8 to 9, forcing regeneration. Production common revision 3 source and executable/library were restored byte-for-byte before launch and verified afterward. No source snapshot or commit receipt was manually rewritten.

The existing full-graphics Freeplay refresh ran muted on a never-activated private Windows desktop at 60 FPS. No builds, tests or independent hashing overlapped the measurement. The fixture has one aggregate retained package containing 23 detected roots and 242 songs; this does not satisfy the independent 20-plus-package coverage requirement.

The refresh completed with an empty queue, no block and successful runtime handoff. Launch to completion was 413.301 seconds; worker time was 411.694 seconds. The preceding uninstrumented binding checkpoint took 411.566 / 409.968 seconds. These are comparable successive runs, not proof of a new regression or improvement.

Independent post-run verification checked all 24,702 owned files (11,296,252,147 bytes) and the transaction receipt with zero mismatches. One character registry differed only in serialization: its previous generated bytes matched the old hash and its parsed JSON was unchanged. All other outputs were byte-identical. The fixture now has valid diagnostic revision-9 receipts; a subsequent forced diagnostic refresh needs a newer diagnostic revision, not edited receipts.

## Direct timings

| Work | Dependency scan | Import conversion's repeat |
|---|---:|---:|
| Root discovery | Already supplied; 0.001 s | 4.857 s |
| Psych-family root song discovery, 22 roots / 231 songs | 35.690 s | 36.174 s |
| V-Slice root song discovery, 1 root / 11 songs | 10.923 s | 10.951 s |
| Duplicate selection | 0.037 s | 0.010 s |
| Complete discovery call | 47.393 s | 52.982 s |

Each complete call returns 242 songs. Candidate gathering includes a small additional legacy-package walk and bookkeeping, so the listed components do not sum exactly. Progress labels are not reliable exclusive timing boundaries: nested discovery reports `scan-roots` while performing other work. Use the direct markers for this conclusion.

The repeated call costs about 12.8% of launch-to-completion time. That is an optimization opportunity, not a promised saving. Preserving freshness and isolating mutable data have costs of their own. Duplicate selection is negligible and is not the next target.

## Next implementation contract

Investigate sharing discovery data only inside the same verified retained-source transaction. Do not introduce a process-wide cache or reuse a previous UI scan after an arbitrary delay.

- Capture an isolated discovery result before `ImportScanJob.perform` mutates `destinationFolder` and diagnostics. Its public `songs` list is a presentation/availability plan and does not retain all conversion data.
- Preserve converted charts, source information, variations, note definitions, characters, stages, root selection, duplicate-source diagnostics and ordering. Reconstruct the per-song source map with existing winner semantics.
- Tie reuse to the exact source snapshot, selected import type, retained-root/engine context, namespace context and active ImportIO transaction. Nested scopes and a later import must not see an earlier result. Incomplete, cancelled or failed scans must never be reusable.
- Preserve source freshness. Determine the existing verification guarantees explicitly; do not treat a path or old receipt alone as proof of unchanged inputs. Any additional verification cost belongs in the end-to-end measurement.
- Keep package display overrides, fingerprint hints, live destination/collision planning, ownership validation, cancellation, staging and publication in the normal import path. Do not reuse scan-mutated destination decisions or bypass transaction checks.
- Direct/manual imports retain their live discovery behavior unless they enter the same verified-snapshot transaction contract. Existing callers and engine dialects keep their fallbacks.
- Compare complete conversion output and receipts, not only song counts. Test changed donor inputs, different selectors/owners, same-named songs, variations, nested scopes, cancellation and scan-result mutation. Measure allocation/serialization costs and repeat the integrated refresh before accepting the change.

Remaining independent-package coverage, final menu handoff, GPU fog/snowfall and CPU/script hitches remain open. All original roadmap requirements remain required.
