# Source Project Context

`SourceProjectContext` models a bounded, project-local subset of Lime 8.3.2's define and environment behavior. It consumes only explicit flags and string values supplied by a caller, plus ordered assignments parsed from retained project files. It does not inspect or mutate the host environment, read Haxelib installations, execute macros, or infer a donor target from the machine running the importer.

The public helper is in `source/SourceProjectContext.hx`. `seed(flags, values, flagsComplete, command)` and the constructor take tri-state presence records separately from string-value records. The optional fourth argument `command` is `null` when uncaptured and `""` when the caller explicitly captured no command. `flagsComplete` defaults to `false`; missing names in a partial context stay unresolved. A complete modeled condition set proves missing names absent only when the command is also known, because Lime conditions separately match `HXProject.command`. The pinned `HXProject` may also seed `environment` from `Sys.environment()`; this helper deliberately does not read that host map, so callers must keep the context partial when uncaptured environment values could affect a condition. Missing or disabled condition symbols remain unresolved when the command is uncaptured. This input is included in the asset-profile build-context fingerprint. Completeness and command survive `clone()` and `mergeNonOverwriting()`.

Presence and value remain distinct. An enabled flag with no captured string value satisfies a bare condition such as `if="FEATURE"`, but `${FEATURE}` is unresolved. A captured value of `"false"` remains present for a bare flag test, while `${FEATURE}` expands to `false` and that condition term fails. A known-absent interpolation keeps Lime's fallback spelling, so `${UNKNOWN}` becomes the literal `UNKNOWN` only when the caller explicitly marked the context complete. An unknown conditional assignment can taint an existing name with `markUnresolved`; a known-active assignment with only an unresolved value can keep its enabled presence with `markValueUnresolved`. An unavailable include uses `markMissingUnresolved` to stop proving absent names while preserving already enabled values. An unresolved dynamic name taints all known names and returns the context to partial mode through `markAllUnresolved`.

`apply()` supports ordered `set`, `define`, `setenv`, `unset`, and `undefine` operations. `setenv` uses Lime's default value `1`; `set` and `define` default to the empty string. All are local to this object. `haxedef` and the compiler-side removal associated with `undefine` are retained as opaque evidence and do not satisfy runtime condition lookups. `valuesSnapshot()` returns effective enabled definitions with known string values in stable name order, retaining their provenance trail.

Conditions preserve the relevant Lime evaluation order: `if` splits raw text on `||` before substitution, while `unless` substitutes the whole expression before splitting. Both split terms on a literal space and trim each term. Presence tests and simple comparisons use the explicit context; bare terms also match the separately captured Lime command even when the corresponding define is absent or unset. Comparisons support Lime's string operators (`==`, `!=`, `<=`, `<`, `>=`, `>`) after removing literal spaces; they do not parse numeric values. An unresolved operand remains unresolved rather than being treated as false.

Interpolation follows the pinned Lime 8.3.2 substitution order: `$${...}` expressions are replaced first using the raw `ProjectHelper.replaceVariable` result wrapped in `${...}`, then ordinary `${...}` expressions are replaced by rescanning the whole string. Define values are not recursively pre-expanded; each subsequent regex pass observes them in the same way Lime does. The regex captures are not trimmed, and exact define lookup occurs before comparison parsing. Bounded repeated-string detection turns Lime's non-terminating cyclic substitutions into an unresolved result rather than claiming a value. Differential coverage extracts the actual `replaceVariable` and `substitute` methods from the pinned Lime checkout into a small Haxe stub project; it compares ordinary and chained values, comparisons, raw whitespace, empty/invalid alias text, substitution order, and nested braces, including the case where `A=${B}`, `B=C`, `C=assets`, and the input is `$${A}`. The same harness extracts Lime's actual `isValidElement` to prove the command token matches independently of a define. Haxelib and Project-object host branches are stubbed and are not invoked. The helper first checks explicit context values, matching Lime's define/environment precedence even for captured names such as `projectDirectory` or `app.file`. Without an explicit value, `haxelib:...`, `projectDirectory`, and dotted reflection fields such as `app.file` remain unresolved, including under `flagsComplete=true`; a complete define set does not attest to the host Project object's properties. Uncaptured names in partial contexts, malformed expressions, and unsupported syntax also remain unresolved with diagnostics. Expansion count, value size, diagnostics, provenance, and opaque compiler records have fixed limits.

For an inline Project include, callers can `clone()` the current context, parse the child in order, and then call `mergeNonOverwriting(child)`. A known parent value wins. An explicitly unset or otherwise known-absent parent name can receive the child's definition. A parent name with unresolved presence is not overwritten. A missing name in a partial parent is also kept unresolved because it may have come from uncaptured Lime build inputs. A complete parent can accept a child definition for a name it proves absent. If the include itself is unresolved, `mergeUnresolved(child)` preserves parent-enabled values and marks known-absent names uncertain when the child could add them; if the child discovers a dynamic name whose effects cannot be enumerated, the parent is downgraded to partial while retaining parent-enabled values.

Focused verification is in `tools/tests/test_source_project_context.py`. It exercises partial and complete missing-name behavior, false-valued flags, ordered mutations, local-only environment behavior, compiler-only haxedefs, Lime differential interpolation, diagnostics, Lime `if`/`unless` split order, and conservative known and unresolved include merges. This helper does not establish donor build target identity or implement general Project.xml parsing; the parser and retained-import integration remain separately scoped.
