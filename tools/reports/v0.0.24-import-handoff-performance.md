# Import completion performance checkpoint

10 October 2026, local v0.0.24. Shared engine/importer changes only. No release or donor/chart edits.

## Changes

- Difficulty support checks pass a fresh directory index to the existing native asset resolver for one synchronous song scan. This avoids repeatedly listing the same directories for absent difficulties. The index is not retained between frames, songs or imports. Exact native hits and positive-cache existence checks remain live; case ambiguity, scope rejection and packaged-asset fallback remain unchanged.
- Committed ownership bookkeeping builds the common path list once with keyed deduplication. Replacement removes all replaced roots once per old path instead of repeatedly filtering that path's owners. Unrelated owners survive. Maps and asset bindings still publish together under the same mutex; no readiness reservation is released early.

Instrumentation wrapped asset resolution and counted directory listings. Each process ran two passes; the first pass discovers new difficulty definitions, so compare matching pass numbers.

Every supported-difficulty array for all 242 songs matched, including order. Both processes exited successfully on a never-activated private desktop. Timing runs had no concurrent builds, tests or hashing workloads. Runtime options were restored. Diagnostic source and binaries are archived under `tmp/v24-handoff-profile-bin` and `tmp/v24-handoff-candidate-bin`; diagnostic source was removed from production. ## Native ownership bookkeeping comparison

A standalone native Haxe executable extracted the old and new bookkeeping methods and used the same committed 24,702-file, 23-root manifest. Manifest loading and output hashing were outside the timed regions. Scheduler cooperation and asset-binding construction were stubbed so this measures the ownership table work alone, not full publication. A mutex stopwatch measured the critical section, without competing readers.

| Pass | Baseline total | Candidate total | Baseline critical section | Candidate critical section |
|---|---:|---:|---:|---:|
| Initial | 7.921 s | 0.363 s | 0.063 s | 0.074 s |
| Replacement | 8.648 s | 0.565 s | 0.708 s | 0.212 s |

Both algorithms produced identical complete ownership tables: 24,698 non-registry paths across 23 roots, SHA-256 `aad2d6663b9e7c2f1fa50bdd0b76f1137de05085d2c6bdc1aae06b4196105b4f`. ## Validation and limits

Focused checks cover new/deleted assets between batches, exact-path precedence, ambiguous case variants, scope rejection, duplicate roots, unrelated/shared owners, removed output, registry exclusion and independent per-root arrays. The 67 ownership/refresh tests and 13 asset/difficulty tests passed (one existing case-sensitive-filesystem skip).

Production Windows build passed: `tmp/v24-handoff-final-build.log`. The full regression suite passed: 2,757 tests across 928 modules in 381.2 seconds, 344 existing skips and zero failures (`tmp/v24-handoff-suite.log`). The native compiler was on PATH and tests used the short Windows fixture directory. Protected-file and punctuation checks passed; the only historical protected-hash difference remains the previously authorized private graphics-test options file.

These improvements do not yet establish a new end-to-end refresh time. The earlier integrated run's 10-12 second frame near publication/cleanup is not fully explained by the isolated critical-section timing. Re-run the integrated refresh before claiming that stall is fixed; include allocation/GC and owner-asset-binding work if it persists. The fixture is one aggregate package with 23 roots, not 23 independently installed packages. Try Harder's larger GPU bottleneck remains open; existing visual fidelity and GPU baseline evidence is unchanged.


## Integrated refresh follow-up

10 October 2026. A private diagnostic build advanced the fixture's valid common revision 6 to 7 solely to trigger a normal retained refresh. Production source and executable/library were restored byte-for-byte to revision 3 before launch and checked again afterward. The run stayed muted on a never-activated private desktop at 60 FPS; no builds, tests or independent hashing overlapped it. All processes are now terminal. The fixture now has valid revision-7 diagnostic receipts and must not be used with production revision 3 as if they were current.

| Measurement | Prior keyed-scan candidate | New handoff candidate |
|---|---:|---:|
| Launch to completion | 450.520 s | 438.878 s |
| Refresh worker | 434.861 s | 432.993 s |
| Largest instrumented update/draw cost | 12,512 ms | 336 ms |
| Largest start-to-start frame gap | 12,513 ms | 10,656 ms |
| Frame gaps above one second | 4,796 and 12,513 ms | 10,656 and 7,041 ms |

The observed launch-time difference is 11.642 seconds (2.58%); worker time differs by only 1.868 seconds. This is a comparison with the prior recorded run, not a new alternating controlled pair. Do not extrapolate the isolated component gains to total import speed. In particular, the sum of the two multi-second gaps did not improve, so the lower update/draw number does not prove improved overall responsiveness.

The temporary ownership profiler measured initial path bookkeeping at 0.193 seconds, binding construction at 4.466 seconds and lock-held publication at 0.093 seconds. After conversion, these were 0.131, 14.557 and 0.167 seconds respectively. Final difficulty/menu handoff contributed about 336 ms. A 10.656-second gap appeared near the binding phase; another 7.041-second gap occurred during staging cleanup. Some callbacks, including the smoke observer's additional browseTick, run after the current update/draw sample is recorded. GC, native scheduling and those callbacks remain hypotheses until instrumented; this run does not establish their cause.

Independent SHA-256 verification checked all 24,702 committed files (11,296,252,147 bytes) and the commit receipt, with zero mismatches. The only output-byte change from the preceding committed manifest was character-registry serialization. Its original generated bytes matched the prior hash, and parsed JSON was identical. No chart, media or semantic registry difference was introduced.

Evidence: `tmp/v24-integrated-handoff1-proof.json`, `tmp/v24-integrated-handoff-comparison.json`, `tmp/v24-integrated-handoff-isolation.json`, the private runtime's `tmp/v23-historical-fields-integrated-handoff1.{jsonl,process.log}`, and `tmp/v24-integrated-handoff-input/manifest.json`. Diagnostic source/binaries are archived under `tmp/v24-integrated-handoff-bin`. The prior passing production build and full suite remain applicable because this follow-up changed no production behavior.

Next instrument native collection/scheduling and all menu poll callbacks around binding construction and cleanup. The binding builder currently validates and normalizes the entire committed file table separately for every root; a single validated per-root index may reduce allocation and work while retaining every receipt/profile check. Conversion also repeats discovery after scanning, but reuse must remain limited to the same verified retained snapshot and must not weaken source freshness, package naming or owner collision resolution. Keep independent-package refresh coverage and the larger GPU work open.
