# Per-scan directory index and real collection baseline

Local v0.0.24 development. All production changes are shared importer logic. No chart, mod or playing-install files were edited.

## Real collection baseline

A fresh private install from the v0.0.23 archive, using the current pre-index v0.0.24 executable, imported the Psych example collection through the real native ImportWorkflow. The muted window ran on a never-activated desktop. Scan: 165.630 seconds. Conversion and publication: 479.950 seconds. Total: 645.582 seconds.

The scan found 23 roots and 459 song candidates, with 242 queued and 217 duplicates, no scan errors and 52 missing-dependency diagnostics. The import reported 242 imported songs, zero failed songs, 18,369 copied assets and 7,495 skipped assets. It also reported 924 diagnostics, including absent Project.xml mapping sources. That successful transaction is not proof of complete compatibility or of a clean asset mapping. Keep those diagnostics open; do not suppress them to make the benchmark green.

Evidence: `tmp/v24-real-library-baseline-result.json`, `tmp/v24-real-library-native.log` and the linked native log in `tmp/v24-real-library-profile/CammieEngine-windows-x64/tmp/`.

## Shared optimization

Case-insensitive file resolution previously reread and sorted a directory for each distinct requested asset name. The scanner now builds one case-keyed ordered index per directory during a scan. Candidate existence and file-type checks remain live. Case-collision ordering remains lower-case lexical order followed by exact spelling, preserving the prior winner. Failed directory reads do not publish partial indexes. Scan success and failure both discard the index; converter helpers outside a scan keep live directory reads so newly written files are visible.

The test fixture resolves 1,000 different names with one directory listing, compares collision order, verifies missing entries, retries failed reads, sees changed files in the next scan and checks cleanup on success/exception and live outside-scan lookups.

## Dependency expansion follow-up

Temporary native timing checkpoints across 1,051 chart inspections attributed 68.879 seconds to implementation JSON inspection and 33.582 seconds to visual fallback checks. These are instrumented section timings, not a final speed comparison. The production source was restored immediately after building the diagnostic executable. Timing evidence: `tmp/v24-scan-section-profile.json` and `tmp/v24-scan-candidate/CammieEngine-windows-x64/tmp/v23-historical-fields-phaseprofile.process.log`.

JSON and script inspection previously expanded asset candidates before dependency() discarded a repeated reference. Shared asset-reference inspection now passes a deferred candidate resolver. The existing dependency identity check runs first, preserving the first reference's origin, searched paths, found/missing result and diagnostic. Different kinds and songs still resolve independently; a resolver failure creates no partial record and can be retried. No asset existence checks or first-occurrence diagnostics are removed.

The focused test sends 1,000 repeated JSON records through the actual inspection methods and verifies two unique resolutions, case variants, owner isolation, missing counts, sentinel references and retry behavior. All 44 related tests passed, with two platform/donor skips. The canonical Windows build passed. The full suite passed: 2,752 tests across 924 modules in 341.8 seconds, 344 skips and zero failures (`tmp/v24-lazy-dependencies-suite.log`).


The production scan took 121.847 seconds against the earlier 164.731-second warm baseline in the same private install: 26.0% less scan time. The directory-index-only build had taken 161.213 seconds, so lazy dependency expansion accounts for most of this gain. The result is still 459 candidates, 242 queued songs and zero scan errors. Every report byte after removing the generated-timestamp line matched the baseline.
