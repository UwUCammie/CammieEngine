# Legacy NV HUD controls and camera-manager safety

8 October 2026. Development v0.0.22, after the published v0.0.21 release. No sub-agents, donor changes or chart-specific production branches.

## Source contract

Historical Nightmare Vision revision `54c53faa9493b1de88051fda7fcb7ff69e4f3950`, `source/meta/states/PlayState.hx`, declares `showRating` and `showCombo` as true and gates rating insertion and combo digits separately. The modern HUD's digit control is `showRatingNum`; its `showCombo` property alone does not gate those digits.

`NightmareVisionLegacyHudControls` routes explicit legacy writes into the existing HUD renderer. Pending writes survive HUD creation; untouched owners retain current HUD preferences. `PlayState.seedNightmareVision` binds both bare script fields and qualified game fields through the existing live-value mechanism. Each state owns its controls; release prevents retained controls from mutating the previous HUD. This implements visibility controls, not complete legacy transient-popup rendering parity.

## Native crash diagnosis and shared repair

Once the HUD field writes succeeded, the legacy callback reached a camera restoration loop with an uninitialized camera. LLDB isolated a native null dereference in Flixel's camera-manager add path. The source loop had removed existing cameras before attempting to add the null entry, so aborting the entire loop would also prevent restoration of valid cameras.

The shared Psych/NV interpreter now wraps camera-manager `add` and `insert` method reads, including captured method references. Null entries produce a diagnostic and return null without entering hxcpp's camera cast; valid calls, arguments, ordering and return identity are preserved. The source loop can continue restoring valid cameras. The existing camera-array assignment check remains separate because array assignment has a different contract. This does not guard arbitrary later mutation of a camera list or claim that an uninitialized source stage is repaired.

## Remaining work

The legacy stage still does not render correctly. Remaining diagnostics include unresolved `gameObjects.shader.ColorSwap`, direct-entry music access during onLoad, and downstream follow/play/zoom accesses after initialization fails. Successful smoke completion demonstrates crash prevention, not visual parity.

A muted private Freeplay test selected the same chart and simulated confirmation but timed out before PlayState (`tmp/v22-menu-library.log`). The reason for the launch rejection was not established; inspect readiness and launch decisions without bypassing them. This attempt does not settle whether the missing music object is a direct-smoke harness difference or a normal-entry engine defect.

Next compare normal entry with the historical source lifecycle, then inventory older qualified classes and constructors. Historical ColorSwap has different uniform/outline semantics from the modern class; do not blindly alias it. Verify SpriteFromSheet's constructor and play signature against the applicable revision before sharing its adapter. Full Phase 2 and all later menu, library management, Freeplay design, sorting and performance requirements remain open and retained.
