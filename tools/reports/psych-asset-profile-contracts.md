# Psych asset profile foundation, v0.0.17

`PsychAssetProfile` parses retained Psych Engine and Nightmare Vision `Project.xml` asset declarations. The manager binds verified profiles to the active import scope, and the shared Psych language publisher consumes their mappings in regular imports and global packs. Other mapped asset publication remains unfinished.

## Resolver contract

`resolveRetained(snapshotContentRoot, snapshotId, rootRelative, sourceEngine, namespace, build, cancelled)` accepts the retained snapshot content directory and source-root identity values supplied by its caller. `cancelled` is an optional callback checked at Project nodes and include boundaries; cancellation raises `ImportWorkCancelled`. The resolver requires a supported Psych Engine or Nightmare Vision label, a safe owner namespace, a safe relative source root, a matching snapshot directory, and a direct `Project.xml` entry in the adjacent schema 2 receipt. It compares the recorded size and SHA-256 with the file bytes before parsing. The caller must first run `ImportSourceSnapshot.verify()` on the complete snapshot. The profile keeps relative root and Project paths, the supplied namespace and engine label, and the Project digest. This resolver does not read an `ImportRefreshManager` record or prove that its caller obtained these values from one.

`resolveUnverified()` can inspect a direct Project.xml for diagnostics. It marks its result `legacy-unverified`, and both walkers refuse it. A Project.xml path inside a directory is not snapshot provenance by itself.

Build context is caller supplied. `target` is informational; flags are explicit `enabled`, `disabled`, or `unresolved` values with optional provenance. String values, the `flagsComplete` bit, and the Lime `command` token are also explicit inputs. A null command means unknown and an empty string means known to be absent. These inputs contribute to the context fingerprint, and conditions that may match an uncaptured command stay unresolved. The manager persists the selected explicit context fields, but automatic capture of the full source build context remains open. No target, desktop platform, compiler define, or official-build flag is inferred from the machine running the importer. Missing conditions stay unresolved. The result reports `complete=false` when a condition or input cannot be resolved.

## Lime and donor behavior represented

The parser follows the pinned donor Project.xml asset conventions: source `path`, optional `rename`, `if` and `unless`, declaration order, nested typed asset entries, include/exclude filters, `type`/`embed`/`library` interpolation, and Lime's default exclusions. The focused matrix uses a self-contained slice of the pinned donor declarations, including translations (`assets/translations` renamed to `assets`), videos, base-game assets, example mods renamed to `mods`, the readme rename, and OpenAL config renames. It checks Windows official 64-bit, Windows nonofficial 64-bit, web, and target-only/missing-flag contexts. This reduced fixture does not assert complete coverage of the full donor Project.xml or all of its build inputs.

Lime 8.3.2 `ProjectXMLParser.isValidElement()` treats `if` as OR-separated clauses whose whitespace-separated terms are ANDed, and applies `unless` to the same expression. Build context keeps explicit tri-state flags, known string values, and a caller-declared `flagsComplete` bit. A complete context can prove an omitted condition flag absent; an incomplete context leaves it unresolved. The result reports both the caller's initial values and final known values after ordered Project operations. `setenv` interpolates its name; `set`, `define`, `unset`, and `undefine` use literal names, and unsupported dynamic names taint the bounded context rather than being rebound to a different symbol. The implementation mirrors `HXProject.filter()` by escaping dots, expanding `*`, prefix-matching includes, and full-matching excludes. Other regex characters, including `?` and character classes, retain Lime's regex behavior. `haxedef` changes compiler flags, not the `defines` map consulted by `isValidElement()`, so it is retained as an opaque input and does not resolve Project conditions.

Local Project includes are parsed inline only from the selected source root and only when each included file is present in the verified snapshot receipt. A directory include follows Lime's `include.lime`, `include.nmml`, `include.xml` preference; file paths are relative to the containing Project file. Repeated includes are replayed with the current parent context, while active ancestry cycles and combined size, depth, file, and node limits are diagnosed. Input files carry ordered path, size, digest, and parent-include metadata. Lime's `noerror` is an attribute-presence check: a known safe local path that is absent is a no-op when the attribute is present, even if its text is `false`. Unresolved, external, or Haxelib paths remain unsupported. Unsupported or unavailable inputs that could conceal mappings set `mappingScopeUnknown`, which both walkers propagate as an unknown deferred scope. The parser accepts Lime's element-root wrappers, including `<extension>`, and walks their children.

Opaque macros, Haxe flags, haxelibs, and Project imports are not executed or searched. Uncaptured variables, values, dynamic mapping attributes, or unsupported includes remain unresolved. These limits prevent an incomplete parse from being described as a complete build asset profile.

## Mapping and language enumeration

`mapPath(candidate, suffix)` maps a safe relative suffix through one enabled candidate's authored rename. `ownerRelative()` returns a path only for destinations under logical `assets/`; destinations such as `mods/` have no imported-owner asset path.

`walkMappedFiles(profile, snapshotContentRoot, onFile, onDiagnostic, cancelled, sourceFilter)` traverses every static mapping candidate and visits ordinary files with any extension. Each enabled event includes its canonical source path, source-relative path, full mapped path, optional owner-relative path, declaration order, byte size, SHA-256, and resolved `type`, `embed`, and `library` metadata. Enabled callbacks can arrive even when the final walk is incomplete, so a publisher must collect the full plan and inspect status and collision projections before copying. Candidate traversal follows declaration order and sorts directory entries. It preserves repeated mapping events for the same source. Distinct source paths reaching the same owner-relative destination are listed in `ambiguousOwnerPaths` and make the walk incomplete.

The optional `sourceFilter` receives `(sourceRelative, mappedPath)` after Lime filters and before hashing. This allows a language publisher to include a source `.lang` file or a non-language file renamed to a `.lang` target without hashing unrelated media. The default is no filter. Filtered walks apply the same predicate to enabled events and known unresolved or disabled file projections. An exception from the predicate makes the walk incomplete and marks the scope unknown.

`deferredSourcePaths` and `deferredOwnerPaths` include files under unresolved candidates plus exact or prefix paths for enabled files that could not be verified or visited. Those projections let a publisher preserve prior managed outputs when a retained source disappears or changes between whole-snapshot verification and the walk. `disabledSourcePaths` and `disabledOwnerPaths` list matching files under known disabled candidates so a legacy collector cannot reintroduce them. `deferredScopeUnknown` is set when a candidate's source, target, filter, unsupported bundle contents, or an unrepresented Project input scope cannot be enumerated safely, including traversal read failures and safety limits. `ambiguousOwnerPaths` is a deduplicated owner-relative path list. Dynamic or malformed filters and paths, read failures, receipt mismatches, and bounded-walk limits add diagnostics and make the walk incomplete. Lime `.bundle` content is not flattened; enabled bundle mappings remain deferred and unresolved instead of being represented as ordinary files.

`walkLanguageFiles(profile, snapshotContentRoot, ...)` remains a purpose-specific enumerator for `.lang` source inputs under enabled, assets-mapped candidates. It shares the generic candidate traversal and receipt-file verifier while retaining the conventional `data` scopes: the current root, shared tree, current-level trees, and recognized base-game or named library scopes. It does not scan sibling roots or `mods/`. Every returned file is checked against the v2 receipt size and SHA-256, in addition to path containment. The enumerator can return known files while marking its walk incomplete if other profile inputs remain unresolved.

## Integration boundary and remaining gaps

Retained-source refresh resolves and binds receipt-bound profiles after snapshot verification and the manager's expected-root and engine checks. `ModuleFunctions` uses `PsychLanguagePublisher` to plan and publish mapped `.lang` files for Psych owners through the existing non-overwrite staging path, with compatibility fallback only for incomplete profiles. The publisher validates the bound source root, engine, namespace, and exact owner destination. The profile parser and generic walker are not yet wired to general all-assets publication. Do not feed Project asset roots into `ImportRootScanner.supplementalAssetRoots`, because the normal importer has distinct copy policies for scanner roots and mapped roots.

This is a language-publication phase, not full Project.xml asset integration. Other mapped files are enumerated by `walkMappedFiles` but are not published through this path. The shared publisher can use a manager-bound authenticated profile in a global-pack workflow when that retained-source scope is available; a standalone legacy v1 global-pack receipt does not provide that profile. The import receipt does not record the full source compiler target, define/value set, command, or macro inputs automatically. The manager currently preserves explicitly supplied flags, values, completeness, and command, but automatic full-context capture remains open. Unsupported Haxelib/external includes, macros, and compiler-side behavior remain out of scope.

## Focused validation

`test_psych_asset_profile.py` captures real schema 2 snapshots and runs `ImportSourceSnapshot.verify()`. It resolves exact pinned Psych and Nightmare Vision Project bytes by digest, exercises a reduced pinned-donor declaration slice across known and missing-flag contexts, tests Lime filter behavior, nested mappings and metadata interpolation, XML-escaped paths, file type coverage, source and target collisions, disabled/unresolved projections, bundle diagnostics, cancellation, and receipt hashing. Project include cases verify wrapper roots, path ordering, containing-file-relative sources, repeated include replay under changed parent values, receipt manifests, include limits, missing-required versus `noerror` optional inputs, unresolved branches, and tampering. A filtered-walk case changes a mapped non-language file after snapshot capture and verifies that the `.lang` predicate avoids hashing it. A missing-file case verifies that a receipt-listed path receives deferred source and owner projections. The fixture also verifies target labels alone do not resolve missing flags, Project tampering is rejected, and the unverified path cannot enumerate files. It does not establish manager-record lookup or importer publication behavior.
