# Source library bootstrap follow-on contracts

This report reviews the remaining v0.0.19 library/bootstrap work against the available Psych and Nightmare Vision source snapshots, the engine's pinned Lime 8.3.2 source, and the current owner-scoped runtime reports. It does not change production behavior or claim new compatibility.

## Evidence boundary

The source inventory records Psych Engine 1.0.4 at `5c67ced` and Nightmare Vision 1.0 at `733165c`; their Project files and revisions are available under `C:/Users/uwucammie/Documents/coding/FNF/fnf_sources`. Nightmare Vision's `.hxpkg` hash is `A4098757C023DAA525D71DFA893B33F74283DCA0D7D9E85EFBED910A9710E4DD`. It pins forked Lime `6421de16b9dfa4fb55c19f12db65d392a57585c8` and OpenFL `b5565adc75511b3e4c8b384ee25ce7401b11ef32`, among other packages. That lock documents dependency intent, not the target, flags, command, or exact build that produced an installed executable. The Psych snapshot has no `.hxpkg` at its root.

The engine's `tools/ensure_lime_uncapped.py` pins upstream Lime 8.3.2 commit `d78d5be8a29de6ad649ffe4684ee435f76fe051b`. The audited Psych and NV `Project.xml` files contain asset mappings, conditions, Haxelib declarations, and compiler flags/macros, but no root `<library>` or `<swf>` declarations. The v19 warm/lazy named-library fixture is useful runtime coverage, not evidence that these two donor Projects exercise named-library bootstrap. The source API inventory is also still broader than this package: `tools/reports/script-api-coverage.md` is a static audit and records 21 NV globals as names-only, 31 missing, and 105 missing / 111 unverified NV PlayState members. In particular, `OpenFlAssets` is names-only there. Keep library coverage and the remaining script API inventory as separate gates.

## Current supported slice

The v19 identity sidecar binds to an exact owner, engine, scope, namespace, retained snapshot, root-relative source, and Project hash. It records Lime IDs/types, owner-relative file paths and hashes, explicit load target, per-entry preload state, and source Project library attributes. `PsychOwnerAssetLibraryCache` constructs a private `lime.utils.AssetLibrary.fromManifest` from verified file-backed entries. Its Futures and library views are owner-scoped and do not enter the process-global Lime or OpenFL registries. This is the accepted on-demand file-backed slice described by `tools/reports/source-asset-library-integration.md` and `tools/reports/runtime-owner-file-backed-library-v019.md`.

The current metadata does not describe the manifest Lime generates from a Project, compiled `className` values, bundle archive contents, or `ManifestResources` startup registration. Preserving Project `Library.embed` and `preload` attributes is not proof of those outputs. The normal `ImportWorkflow` call to `ImportRefreshManager.importOnce` does not pass `sourceBuildContexts`; the optional explicit context is used by focused fixtures. Thus a target-dependent load profile must remain incomplete on ordinary imports unless an exact context is supplied. Do not infer `cpp`, `desktop`, `officialBuild`, `MODS_ALLOWED`, or a complete define set from the importing host or an executable's filename.

## Lime contracts that set the boundary

The local Lime `AssetHelper.createManifests()` builds namespace manifests from actual `HXProject.assets` and their `asset.library` values, with a default manifest when needed. A Project declaration alone must not be turned into a runtime claim unless generated output proves that a library exists. `processLibraries()` can add implicit default/named libraries, set default preload behavior, generate manifest assets, call external library handlers, or generate packed outputs. Those steps affect what runtime `Assets` sees; they are not equivalent to reading the Project XML library list.

`AssetHelper.getAssetData()` is target-sensitive. In the pinned upstream source, HTML5 fonts become generated classes and preload; HTML5 sound/music can be grouped as `pathGroup`; Flash/AIR and WebAssembly have different embed/preload rules; the other target branch emits a class name for embedded assets or fonts and a path otherwise. `processLibraries()` also decides whether a generated manifest is embedded based on its output entries, including whether every entry has a `className`. The Project library `embed` property and an asset's `embed` property are distinct inputs, and neither alone says whether generated startup code registers an embedded manifest.

`ManifestResources.hx` registers an embedded manifest with `Assets.registerLibrary`; for a file manifest it records a path, then arranges preload objects/names. Embedded bundles use `AssetBundle.fromBytes` and register a bundle-backed library. The current owner runtime intentionally does not mutate those global maps. That protects same-name owner isolation, but it means the v19 test does not establish source-identical startup `getLibrary()` visibility or automatic preload.

Custom handler libraries are a separate trust boundary. Lime serializes an `HXProject`, calls `Haxelib.runCommand(..., "process", ...)` for each handler, and merges the returned Project. Built-in `pak`, `pack`, `gzip`, `zip`, and `deflate` library types are transformed into a packed file plus a manifest whose `libraryType` and `libraryArgs` select a runtime class. They cannot be represented by copying the original source files into a normal file manifest and calling that parity.

Bundles and class-backed APIs need distinct evidence. `ProjectXMLParser.parseAssetsElementLibrary()` may read an included Project file or `library.json`, preserve manifest IDs, and expand files below a `.bundle` directory. `AssetBundle.__extractBundle()` reads every ZIP entry and decompresses it into memory; the pinned implementation has no entry-count, expanded-size, ratio, or path-containment policy. OpenFL `Assets.getMovieClip()` resolves a `MOVIE_CLIP` ID through a library, while generated `className` / binding behavior relies on classes and global binding registration. A name-to-file alias is insufficient to create the missing compiled class or MovieClip.

## Recommended next bounded package

After the active typed-media/library changes pass their gate, first add an owner-local standard-manifest bootstrap contract, not general custom library or class support. Reuse `PsychAssetProfile`'s receipt-bound Project and `SourceProjectContext`, `ImportRefreshManager.ownerAssetIndexBinding()`, the immutable identity publication, and the existing per-owner library cache. Do not add another Project parser or register imported names in `lime.utils.Assets` / `openfl.utils.Assets`.

Build a differential fixture around the pinned `AssetHelper.processLibraries()` plus `createManifests()` and `ManifestResources` output. Record the generated result needed by the owner runtime: actual library namespace, generated manifest kind (embedded manifest, file manifest, bundle, packed/custom, or unresolved), manifest root/path rules, per-entry `path` versus `className` or `pathGroup`, and library/preloader ordering. The source parser's `ProjectLibrary` values remain source inputs; the generated manifest result is the authority for runtime claims. If a class-backed entry is not present as a verified compiled class in this engine, keep that library unavailable with a diagnostic. Do not reinterpret it as a raw path silently.

Add a manager binding for an explicit, complete source build context tied to the exact snapshot, root, engine, Project digest, and context fingerprint. The ordinary UI import path currently supplies none. A context provider must report its evidence source and completeness, including target, command, flags/values, and unsupported external inputs; absent proof remains `unknown`. The NV `.hxpkg` can help identify intended package versions but cannot fill in the target or defines, and the Psych source does not have an equivalent root lock in the audited snapshot.

At runtime, mirror only generated *standard file-manifest* startup ordering in a private owner registry. Keep its library map, loaded Futures, preload queue, release, and same-name handling inside the verified owner identity. Prove that same-name global Lime/OpenFL libraries remain unchanged. Treat unknown or unsupported generated forms as blocked, rather than allowing host/global fallback for a namespace the imported owner claims. Preserve existing on-demand `loadLibrary()` behavior where source semantics do not require startup visibility.

Focused acceptance should cover default and named libraries; implicit versus authored namespace; duplicate declaration and asset ordering; Project `preload` and `embed` versus per-asset `embed`; target-specific font and sound/music behavior; absent target; unresolved defines; empty configuration declarations versus actual generated libraries; stale binding and owner release; and two owners with identical library names. The oracle should compare actual generated manifest fields, not reimplement expected answers in test literals. A small real retained import should publish and load one known standard library, then show that an incomplete build context rejects load without touching a same-named global.

## Keep these as separate work packages

- **Bundle assets/libraries:** Add a receipt-bound bundle index and owner-private loader only after a bounded archive policy exists. Enforce compressed and expanded byte limits, entry count, duplicate/path validation, cancellation, and owner containment before using Lime's archive reader. Test malformed archives and preservation of existing managed outputs. Do not call Lime's unbounded full-memory extraction directly on untrusted retained bundles.
- **Packed/custom handlers and generated libraries:** Keep unsupported until output can be produced from an explicit, pinned, safe build/handler contract. Do not run Haxelib handlers, macros, or imported compiler input during routine refresh. A retained already-generated artifact would need its own authenticated format and provenance.
- **Class bindings and MovieClip:** Keep guarded until a compiled owner class/binding artifact and isolated class registry exist. The importer must not synthesize or globally register `Type` names from XML. Test class identity, duplicate names across owners, failed class resolution, and teardown before advertising this API.
- **Source build capture:** This is a prerequisite, not a guessed default. The Project files contain `if` / `unless`, haxelibs and Haxe macros; `.hxpkg` is dependency metadata, not a captured compiler invocation. Until the exact source context is available, keep target-dependent profiles incomplete and report which input is missing.
- **Cross-owner mapped core assets:** Continue to use only exact receipt-bound owner/profile bindings. Do not clone one root's profile into a sibling namespace; a future package needs manager-authenticated provider-to-receiver provenance and transaction ownership.

This proposal is limited to source contracts and work ordering. No production or test files were changed and no build, test suite, or game launch was run for this review.
