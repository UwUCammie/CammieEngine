# v0.0.34 removal interface and asynchronous handoff evidence

This report covers the removal interface, its worker/main-thread boundary, and independent partition safety review. The final removal probe passed at 60 FPS and unlimited pacing against integration build10. The release candidate advanced beyond build10 after that run; builds after15 change only opt-in menu probes/diagnostics. Production changes after build10 concern imported-menu routing, controls, missing diagnostic artwork and shared ownership of returned HXC tweens, alongside opt-in probe corrections. Removal UI/backend production code is unchanged; the shared interpreter resource-ownership fix also applies to globally loaded menu modules. This report identifies the actual tested executable and does not claim removal was rerun against the final menu candidate.

## Implemented interface

`LibraryActionsSubState` offers removal only for imported package roots. `LibraryRemovalSubState` shows a concrete preview from the worker: human package title and stable package badge, exclusive managed file count, shared managed file count preserved, retained snapshot counts, registry contribution count, and preserved scores/favorites/categories/difficulty history. The compiled bundled results owner is protected by `BundledImportOwnership`, matching the package baseline rather than editable user metadata.

Cancel is the first confirmation action. Busy preview and incomplete/blocking inventories cannot confirm. The operation remains open while a worker performs cancellation and rollback. Once a durable commit is reported, Cancel disappears and cleanup continues. Cleanup-pending and conflict states offer explicit retry. Interrupted startup recovery is also retryable, including when the initial package preview could not begin. Library actions exposes a generic recovery entry without a selected chart or owner, so an interrupted removal whose package row has disappeared can still be recovered without beginning a new deletion. Global native Freeplay routes generic recovery through the neutral management state so live global modules cannot prevent the exclusive recovery reservation indefinitely; a scoped authored caller explains that it must return to Imported Mods first. A temporarily busy importer does not discard the cleanup-pending state or its retry action.

`ImportRemovalManager` performs filesystem preview, apply, and recovery on workers. It snapshots active source/menu owners on the foreground thread, checks them again before confirmation, and acquires the importer reservation before apply. Startup recovery acquires the global reservation before the initial game state is created. Completion is exposed only after the foreground cache/library handoff. A worker commit survives a later foreground publication error as recovery knowledge, so retry cannot claim a committed removal was cancelled.

Active authored sessions and scoped callers remain protected. The interface explains that an active package must be removed from Imported Mods after its resources are released. It does not erase or ignore a live resource lease to make confirmation pass. A selected globally loaded HXC module routes through the typed `LibraryRemovalState`: the old Freeplay is destroyed first, its source resources are disposed, and only then does the neutral host state create the removal confirmation. Cancel returns to a new Freeplay through the existing departure bookmark. The neutral state keeps unrelated queued importer work moving. Actual source resource disposal and atomic menu lease acquisition belong to the imported-menu implementation; its separate candidate18 native acceptance passed at both pacing settings. See the menu report for bounded source contracts and tracked resource counts.

## Focused executable checks

The following owned modules pass on the portable Haxe interpreter:

- `test_library_removal_ui.py`: compiles the actual confirmation substate with deterministic worker snapshots; checks default Cancel, concrete content/history text, progress cancellation, no success before publication, exactly-once published callback, cleanup retry, blocked confirmation, bundled host protection, and stable keyboard navigation to cold startup recovery retry.
- `test_import_removal_manager.py`: compiles the actual manager with asynchronous worker fixtures; checks startup exclusion, incomplete preview denial, active-owner change before confirmation, confirmed reservation, cancellation restoration before release, committed foreground publication, cleanup retry, preservation of pending retry while another importer is busy, unresolved rollback reservation, successful recovery release, and gameplay exclusion.
- `test_bundled_import_ownership.py`: matches the compiled protected namespace to the clean Windows packager constant and ensures the helper does not infer host ownership from editable installed files.
- `test_import_removal_partition_safety.py`: exercises the actual partition helper; verifies full-selected plus partial-survivor sharing, overlapping partial transaction sharing, and a new category whose human name equals a removed chart folder while another chart survives.

These are targeted checks, not a replacement for the integrated suite or native acceptance.

## Independent backend review

Material findings reported to the backend owner and orchestrator included retained snapshot cleanup, recovery journal authorization, importer queue exclusion, token validation before foreground mutation, receipt-committed cleanup failures, full/partial shared-file attribution, category-name collisions, and unclaimed local files inside a removed namespace. The sharing and category regressions are pinned by the independent executable test above. Release acceptance must also include the backend owner's receipt, crash/restart, edited-file, dependency, and aggregate transaction checks.

## Prepared native fixtures

`tools/prepare_library_removal_native.py` creates a unique private runtime beneath `tmp/v34-removal-smoke` from the v0.0.33 release ZIP, plus a generated one-song Psych source. It does not copy a user installation or live import cache. Successful 60 FPS and unlimited runtimes are `fe993ba89869/runtime` and `f675f52b4b91/runtime` respectively.

`RuntimeLibraryRemovalProbe` is an explicit smoke opt-in. It requires a generated private-runtime request and isolated smoke saves. The probe uses the actual converter, actual Library actions and confirmation UI, dispatched keyboard Accept, actual worker removal and main-thread publication, native Freeplay reconstruction, and a second fresh-process package/receipt absence, archived identity and persisted history check before reinstall identity/history checks. The runner compares generated source file hashes before and after both native processes.

`tmp/v34-hidden-removal.py` runs the probe on a private Windows desktop that is never activated, with muted runtime audio and a private save root. It copies the final executable and native library only when the orchestrator authorizes native launch after the build. No game was launched during fixture preparation.


## Native acceptance

Four native processes exited successfully: removal followed by a fresh restart/reinstall at each pacing. The tested executable SHA-256 is `4a4dfc21dd934c5e85b4675102a5095cb6e6a1703be12985500f8b492c5c0659`. Both `tmp/v34-removal-smoke/fe993ba89869/native-proof.json` and `tmp/v34-removal-smoke/f675f52b4b91/native-proof.json` record unchanged generated source files, fresh-process removal absence and preserved reinstall history.

The actual native confirmation selected Cancel first and displayed the human package name, 12 managed files at 60 FPS (13 in the unlimited fixture, which additionally retained a generated synthetic WAV), shared-preserved count, snapshot/registry counts and preserved-history text. Cancel left the package and library generation unchanged. A later keyboard confirmation completed the real worker transaction, published on the main thread, and refreshed the same native Freeplay. The second process verified catalog and physical owner/chart-directory absence, reconciled retained receipts and archived identity, plus persisted favorite, category and selected difficulty. Reimport reused the stable identity and preserved that history. Actual confirmation and restart-absence framebuffer captures at both pacing settings were visually inspected: readable, with no overlap or clipping.

Logs: `tmp/v34-removal-native60.log` (successful first game process followed by a runner-only marker-parser error), `tmp/v34-removal-native60-restart.log` (continued fresh process and final proof), and `tmp/v34-removal-native-unlimited.log` (both processes and final proof). The parser correction required no engine change. Earlier opt-in failures are retained separately: canonical runtime-path spelling, waiting for foreground generation publication, and waiting for Flixel's deferred substate creation. The final probe checks the actual created modal on a later frame rather than weakening the assertion.

These native runs prove the real default-Cancel/confirm UI, foreground publication, restart absence and reinstall history for a generated single-package fixture. Shared-file/dependency/partial-aggregate/crash recovery and conflict/cleanup retry are covered by executable transaction and state-machine fixtures, not fault injection into this native UI run. Native score records and physical-controller input were not populated/exercised. Broader authored-menu/API/resource acceptance remains separately documented by the menu owner; no full-roadmap completion is claimed. All native work used generated source, private runtime copies, isolated saves and muted never-activated desktops.
